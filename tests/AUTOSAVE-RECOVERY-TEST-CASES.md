# 自动保存元数据容器与崩溃恢复 — 手测用例

范围：自动保存的落盘容器（sidecar 元数据）、崩溃恢复、「存回原位」。**只测这条线**，不涉及其它已通过的基线。

协议层（唯一命名 / 先写 sidecar / 读时自证 / 按 `savedAtUnixMs` 排序 / History 整对轮换）已由
`tests/TuneLab.Tests/AutoSaveStoreTests.cs` 的 11 条单测覆盖，本文档只列**必须在跑起来的界面上验证**的部分。

自动保存目录：`%APPDATA%\TuneLab\AutoSave\`（哨兵在根，历史在 `History\`）。
制造"崩溃"用任务管理器结束 TuneLab 进程（**不要**正常关闭——正常退出会清掉哨兵，这本身就是用例 5）。

---

## 1. 元数据落盘形态

1. 打开任意工程并保存到某处（例如 `D:\test\MySong.tlpx`）。
2. 改一个音符，等自动保存间隔（设置 > 通用，默认 10 秒）过去。
3. 看 `AutoSave\` 根目录。

**预期**：根下有**一对**同名文件 `<时间戳>_MySong.tlpx` + `<时间戳>_MySong.json`；
时间戳带毫秒；`History\` 里也有同样的一对。

`.json` 内容形如：

```json
{
  "SchemaVersion": 1,
  "AutoSaveFile": "2026-07-29_10-00-00-123_MySong.tlpx",
  "SavedAtUnixMs": 1785000000123,
  "ProjectName": "MySong.tlpx",
  "OriginalPath": "D:\\test\\MySong.tlpx"
}
```

要点：`AutoSaveFile` 与同目录那个 tlpx 的实际文件名**逐字符相同**；`ProjectName` 是原样展示名（带扩展名）；
文件名里**不出现** `.tlpx.tlpx`。

## 2. 崩溃恢复：提示指明工程，显示名不再靠切文件名

1. 承用例 1 的状态（有未保存改动、哨兵已生成），结束进程。
2. 重新启动 TuneLab，看"上次异常退出"提示。

**预期**：提示里除原本那句问话外，还显示**工程名**（`MySong.tlpx`）与**原工程完整路径**
（`D:\test\MySong.tlpx`）——用户不必先恢复出来才知道它指的是哪个工程。

3. 选确认。

**预期**：恢复出工程内容；标题栏显示 `MySong.tlpx`（来自 `ProjectName`，不是从文件名切出来的），
且带未保存标记；文件菜单里出现「存回原位」项。

**反向检查**：把某个 sidecar 的 `ProjectName` 改成一个很短的字符串（如 `X`）再走一遍——
标题应显示 `X` 而不报错、不越界。旧实现按固定长度切前缀，短名字会出问题。

## 3. 崩溃恢复：相对音频引用可解析（本次的核心改善）

1. 新建工程，把一个 wav **放在工程文件旁边**（如 `D:\test\vocal.wav`，工程存为 `D:\test\MySong.tlpx`），
   导入该音频成音频 part，保存。
2. 确认 tlpx 里该 part 的路径存成了相对形态（以 `..` 开头）。
3. 改点东西让工程变脏，等自动保存，然后结束进程。
4. 重启并恢复。

**预期**：音频 part **正常显示波形、能播放**（基准目录来自 sidecar 的 `OriginalPath` 所在目录）。
这正是改动前会断链的场景——恢复出来的工程没有保存路径，于是相对引用无处可解。

**注意**：工程仍是未保存态。这是刻意的——一次 Ctrl+S 不该用崩溃时的中间状态覆盖原文件。

## 4. 「存回原位」

1. 承用例 3 的恢复态，文件菜单 →「存回原位」。

**预期**：确认框显示**完整目标路径**（`D:\test\MySong.tlpx`）；
选取消则什么都不发生；选替换则原文件被替换成恢复的内容，此后工程变为已保存态、标题栏去掉未保存标记，
「存回原位」项随之消失（它已经是一个正常保存的工程了）。

**边界**：确认框弹出后、按替换之前，先到资源管理器把原文件删掉或改名 → 按替换应**什么都不写**并记错误日志，
不会凭空新建一个文件。

## 5. 正常退出不留哨兵

1. 正常保存并关闭 TuneLab。
2. 重新启动。

**预期**：不弹恢复提示；`AutoSave\` 根目录为空（`History\` 保留）。

## 6. 降级：元数据缺失或配不上

三种情形各走一遍（每次都先造出一对哨兵，再手工破坏，然后启动）：

| 手工破坏 | 预期 |
|---|---|
| 删掉 `.json` | 仍弹恢复提示、能恢复内容；提示里只显示自动保存的文件名、**不显示原路径**；标题显示文件名；**没有**「存回原位」项；相对音频引用断链（缺失态） |
| 把 `.json` 里 `AutoSaveFile` 改成别的名字 | 同上（校验不通过 → 当作无元数据） |
| 把 `.json` 内容改成非法 JSON | 同上，且日志里有一条跳过损坏元数据的警告 |

要点：**一律优雅降级**，不弹报错、不崩、不猜路径。

## 7. 从未保存过的工程

1. 新建工程（不保存），随便改点东西，等自动保存，结束进程。
2. 重启并恢复。

**预期**：能恢复内容；`OriginalPath` 为 `null`（sidecar 里干脆没有这个键）；
提示里只显示"未命名工程"、**不显示路径行**（本来就没有原位）；
**没有**「存回原位」项；标题显示"未命名工程"。

**sidecar 里 `ProjectName` 应为空串**——元数据**绝不存本地化文本**，"未命名工程"由界面按当前语言渲染。
文件名也因此只剩时间戳（不带本地化文字、不引入非 ASCII 字符）。

**反向检查（i18n）**：造出这份哨兵后**先改界面语言**（设置 > 通用 > 语言，例如切成 English）再重启恢复 →
提示与标题应显示**新语言**的 "Untitled Project"，而不是造哨兵时那个语言的字样。
若这里显示旧语言，说明有本地化文本被写进了元数据。

## 8. 从恢复态再崩一次

1. 承用例 3 的恢复态（未保存），继续改点东西，等自动保存，再结束进程。
2. 重启并恢复。

**预期**：新写的 sidecar 里 `OriginalPath` **仍指向最初那个工程文件**，
于是第二次恢复后相对音频引用照样能解析、「存回原位」照样可用。
（若这里丢了原路径，就意味着"恢复态"是个会衰减的状态，用户崩两次就找不回原位置了。）

## 9. 切换工程时的哨兵

1. 造出哨兵（有未保存改动 + 等过自动保存）。
2. **不结束进程**，直接在应用内打开另一个工程（未保存提示选"否"）。

**预期**：`AutoSave\` 根目录被清空（切换工程即放弃上一个工程的崩溃哨兵，与改动前一致）；
`History\` 不受影响。

## 10. History 轮换

1. 把设置 > 通用 > 自动保存最大数量设为 3。
2. 持续编辑，让自动保存跑 5 次以上。

**预期**：`History\` 里最多 3 **对**文件（每个 tlpx 都配着自己的 json，不出现落单的半对）；
被淘汰的是 `SavedAtUnixMs` 最小的那些。

**反向检查**：把 `History\` 里某个文件的"修改时间"改成很早/很晚（属性或脚本），轮换结果**不应改变**——
排序只看 `SavedAtUnixMs`，不看文件系统时间。
